01 Program objective

What this program is actually trying to do

Read one integer n, then print every prime number between 2 and n inclusive on a single line, separated by spaces. If n is below 2, print an error message instead. The program runs once and exits.

purpose

List the primes up to a limit. pInRange walks i from 2 to num and, for each value, asks isPrime(i) a single question: “does anything divide this number?” If the answer is true the number is printed followed by a space; if false it is silently skipped.

The program solves enumeration, not just classification. The previous program judged one number; this one reuses a one-number judge as the inner step of a range scan — which is the whole idea of composition.

learning

Practising how one static method can be called from inside another, and why a boolean return type is enough to drive a loop.

  • boolean returns with a guard clause and an early exit;
  • a method call inside a loop — 19 calls for n = 20;
  • the √n bound, and why testing every integer up to n − 1 is unnecessary;
  • Math.sqrt and the int ↔ double promotion inside a loop condition;
  • a void method whose only output is printed text;
  • print versus println, and where the spaces come from.

behaviour

Printed immediately: a blank line, then Enter max value : , then the read blocks.

After a valid n ≥ 2: one blank line, one line of space-separated primes ending with a trailing space, then a final newline.

After n < 2: one blank line, then Invalid Input!! and a newline. Nothing is computed — pInRange is never called.

After a non-integer: an InputMismatchException stack trace at line 29, and the program stops before sc.close().

02 Problem statement

The task, stated without the code

Given a maximum value n, output every prime number p with 2 ≤ p ≤ n, in ascending order, on one line, each followed by a space. Reject any n < 2 with the fixed text Invalid Input!!.

Input, output, rules

Input. One integer token, typed after the prompt Enter max value : . Note that the prompt is printed with println, so the typed digits appear on the line below the prompt, not after it. Only an int is accepted: no decimals, no words, nothing outside −2,147,483,648 … 2,147,483,647.

Output. For n ≥ 2: the primes in [2, n] separated by single spaces, with a separator after the last one as well, so the line ends with a trailing space before the newline. For n < 2: Invalid Input!! — two exclamation marks, no trailing space.

Rules. A number num is prime when it is ≥ 2 and no integer i with 2 ≤ i ≤ Math.sqrt(num) divides it exactly. The range scan must start at 2, because 0 and 1 are never printed.

Constraints. Nothing is stored: no array, no list, no string being built up. The cost is the sum of the per-number checks, so it grows faster than linearly in n. There is no retry loop — one run, one answer.

The exact output contract

⏎ blank line — println() at line 27 Enter max value : ⏎ println at line 28 20 ← what you type (echoed by your terminal) ⏎ blank line — println() at line 30 2 3 5 7 11 13 17 19 ← print() at line 20, then println() at line 36
  • Three blank lines are part of the output and come from three empty println() calls.
  • The trailing space before the newline is real output, produced by print(i + " "). It is not visible in a terminal, which is why exact-output comparisons often trip on it.
  • No separator before the first prime: the space belongs to each number, not to the join between numbers.

For n = 20 that is 19 calls and 25 modulo tests to print 8 numbers. Composites are cheap — most are rejected at i = 2 — while primes are the expensive case, because they run the loop to the end and still return true.

A prime number p costs floor(√p) − 1 tests; an even number costs exactly 1. The whole program's cost is dominated by the primes it prints.
03 Core logic & approach

Ask a yes/no question once per number

The program is split by responsibility, not by convenience: isPrime knows how to judge one number, pInRange knows the range and the printing, and main knows about input and validation. Each one calls the next.

The call chain

main(String[] args)
Reads n, validates it, then makes exactly one call.
→
pInRange(int num)
Loops i = 2 … num. Calls isPrime(i) once per value. Prints the trues.

Three static methods, no objects. The inner method is called n − 1 times per run, each call with its own fresh copy of num and its own loop variable.

int n = sc.nextInt(); — the only input the program ever reads.
↓

Yes → print Invalid Input!! and skip computation entirely. 0, 1 and every negative number are handled by this single test, in main, before anything else runs.
↓ no
3 · pInRange(n)
Loop i = 2; i <= num; i++. The bound is inclusive, so n itself is tested — that is how 19 gets printed for n = 20… and how 20 does not.
↓ each i

Guard num < 2 → false; then test i = 2 … floor(√num); return false at the first exact divisor, true if the loop finishes.
↓ true
5 · print(i + " ")
The number and its separator, with no line break. After the loop, main's final println() ends the line.

Steps 3 and 4 are nested loops: about n outer iterations, each running a short inner loop.

Why the square root is enough

Suppose num has a divisor d larger than √num. Then the partner num / d is smaller than √num, and it divides num just as well. Divisors always come in pairs that straddle the square root — so if no divisor exists at or below √num, none exists at all.

36 ÷ 136 ÷ 236 ÷ 336 ÷ 436 ÷ 6
1 × 362 × 183 × 124 × 96 × 6

Everything left of the middle column has a partner on the right. So √36 = 6 is the last new information — testing 7, 8, 9 … 35 would only re-discover factors already found. That single observation is what turns 95 tests for 97 into 8 tests.

Why the early return matters just as much

return false; inside the loop is not a stylistic choice — it ends the method. The moment a divisor is found, the remaining candidates are irrelevant, so the loop stops without any flag, counter or break. Conversely return true is reachable only by falling out of the loop, which is precisely Java's way of saying “no divisor was found”.

Correct by construction. The method has exactly two exits and both are justified: false because a witness exists, true because the complete search space 2 … √num was exhausted. There is no third case to mishandle.
04 Key Java concepts

What the code is actually demonstrating

Nine ideas carry this program. Each card says what the concept does here, why it is used, and what to keep.

boolean return

isPrime returns boolean, so the answer is exactly the two things the question allows. The caller writes if (isPrime(i)) — no comparison needed, because the value already is the condition.

Why: a yes/no question deserves a two-valued type. Learn: boolean values can be used directly as conditions; if (isPrime(i) == true) would be redundant.

guard clause

The first three lines handle num < 2 and leave. Everything after them can assume num ≥ 2, which is why the loop needs no extra checks.

Why: it removes the edge cases from the main path instead of sprinkling conditions through it. Learn: handle the impossible/edge input first and return early; the rest of the method then reads like the happy path.

method call chain

main calls pInRange once; pInRange calls isPrime once per number; isPrime calls Math.sqrt once per test. Three levels of “someone else does this part”.

Why: each method has one job and can be tested alone. Learn: a method call is a pause — the caller waits, the callee runs, then control and a value come back.

nested loops

Two loops are involved, in different methods: pInRange's i runs 2 … n, and inside each call isPrime's own i runs 2 … √num.

Why: enumeration needs an outer walk and a per-item test. Learn: the two i variables are different variables in different scopes — the inner one cannot touch the outer one, despite the identical name.

Math.sqrt

The loop condition is i <= Math.sqrt(num). Math.sqrt takes a double and returns a double, so i is widened to double for the comparison.

Why: it gives the mathematical bound without computing i * i, which could overflow int. Learn: mixed-type comparisons promote automatically, and <= vs < matters — a perfect square has √num exactly equal to its divisor.

early return

return false; at line 11 leaves the method mid-loop. For num = 20 that happens at i = 2, so 2 of the ~3.5 possible iterations are skipped.

Why: one witness is enough to prove compositeness. Learn: return inside a loop exits both the loop and the method — no break, no flag variable.

void + side effect

pInRange returns nothing. Its entire result is the characters it sends to System.out: the caller learns nothing programmatically, and the primes are not stored anywhere.

Why: for a print-the-answer exercise, printing is the deliverable. Learn: a void method's effect is a side effect — irreversible, invisible to the caller, and impossible to reuse without printing again.

print vs println

System.out.print(i + " ") writes without ending the line, which is why all the primes land on one row. The pair of blank println() calls in main produce empty lines, and the final println() supplies the missing line break.

Why: the layout is being built one piece at a time. Learn: print + explicit separators give full control — and a trailing separator is part of the output, whether you can see it or not.

Scanner · one-shot

sc.nextInt() reads a single token. There is no do-while and no second prompt: this program answers one question per launch, then sc.close() runs and main ends.

Why: the task asks for one range. Learn: closing the scanner is correct and cheap — and it is skipped entirely if nextInt() throws, which is the gap this design still has.

Boundary — 2

Limitation — abc and huge n

Letters and decimals make sc.nextInt() throw InputMismatchException; nothing catches it, so the program dies at line 29. And because the cost grows like n√n, a very large n does not crash — it simply never finishes. The simulator caps its own work and says so rather than freezing.

08 Edge cases, correctness & limitations

What the implementation does — and what it does not

The mathematical part is correct for every n the program accepts. What it does not do is defend itself against input it cannot parse, and it does far more work than a range query needs.

Limitations in this implementation

  • No input validation. sc.nextInt() is called with nothing guarding it: no hasNextInt(), no try / catch. One wrong keystroke ends the run with a stack trace, and sc.close() at line 37 is skipped.
  • One query per launch. There is no retry loop, so testing five values means five runs. (Good news: unlike the previous program, this one does terminate on invalid input.)
  • Math.sqrt is recomputed on every loop check. The condition i <= Math.sqrt(num) runs the square root once before the first iteration and again after every increment — about √num + 1 calls per number. Hoisting it (int limit = (int) Math.sqrt(num);) removes nearly all of that overhead.
  • The result is not reusable. pInRange returns void and prints inside the loop, so the primes cannot be counted, stored, sorted or re-printed by the caller.
  • Fragile exact output. Three blank lines and a trailing space are part of the transcript; an autograder comparing strings, or a human reading a terminal, can easily disagree about them.
  • pInRange has no guard of its own. Called directly with 1 or a negative number it prints an empty line rather than a message — the validation lives only in main, so the method is not safe to reuse as-is.
  • The wrong algorithm for the job. Testing each number independently repeats a huge amount of work; a range of primes is better produced by a sieve, which crosses numbers off instead of re-deriving each one.

Correctness, stated carefully

For every n ≥ 2: the list is correct. Each k in 2 … n is tested against every candidate from 2 to floor(√k). If none divides it, no larger divisor can exist either — the partner would be smaller than the root — so true is justified. If one does divide it, false is justified by that witness. Both outcomes are proven, never guessed.

The square root bound is exact here. Math.sqrt is specified to return the correctly rounded result, and every perfect square of an int is exactly representable as a double, so Math.sqrt(49) is exactly 7.0 and the <= comparison catches the divisor 7. Writing < instead would silently mis-classify every odd perfect square (9, 25, 49 …).

It also avoids an overflow trap. The common alternative i * i <= num is exact only while i * i fits in an int; above 46,340 it overflows and the loop can stop early. Comparing against Math.sqrt(num) keeps the arithmetic in double, where large int values are exact.

For n < 2: handled, by design. The rejection happens in main before any call, so isPrime's own num < 2 guard is only ever exercised if someone calls it directly. That guard is still correct — it returns false for 0, 1 and negatives.

09 Time & space complexity

Cheap per number, expensive per range

Two different questions have two different answers: one call to isPrime(n) is Θ(√n), but printing every prime up to n costs the sum of those calls.

Time — O(√num) per call, O(n√n) per run

Inside isPrime the loop runs at most floor(√num) − 1 times, so a single query is Θ(1) for even numbers (rejected at i = 2) and Θ(√num) for primes, which exhaust the loop.

pInRange calls it n − 1 times, so the run totals Σ √k for k = 2 … n, which is Θ(n√n). The constant is small because composites usually exit after one test — the measured totals below say it precisely.

Space — Θ(1)

Nothing is allocated per number. At the deepest point the stack holds three frames (main → pInRange → isPrime), each with an int or two, plus the Scanner's fixed input buffer. The primes go straight to the output stream and are forgotten — memory does not grow with n even though the printed line does.

What would actually be faster

A sieve of Eratosthenes answers the same question in O(n log log n) time with O(n) extra space: mark the multiples of each prime once and read off what is left. For n = 10⁶ that is a few million marking operations instead of 67 million modulo tests and 67 million Math.sqrt calls — and the gap widens as n grows.

The trade is memory for time. This program's Θ(1) space is genuinely elegant for a single query; it is the wrong tool only because it is being asked the same question n times.
10 Takeaways & future connections

What this program teaches

lesson

A boolean method can be the inner step of a loop. pInRange contains no primality logic at all — it just repeats a question it does not know how to answer. Composing a small, correct decision into a larger scan is the most reusable pattern in this whole exercise: isPrime stayed unchanged while the range logic was written around it.

mistakes to avoid

  • Writing i < Math.sqrt(num) — it misses 9, 25, 49 and every other odd perfect square.
  • Using i * i <= num in int arithmetic near Integer.MAX_VALUE, where i * i overflows.
  • Starting the range at 1, or testing i < num instead of <= num, so the limit itself is never checked.
  • Recomputing Math.sqrt(num) in the loop condition instead of storing it.
  • Reading with nextInt() without hasNextInt().
  • Forgetting that print leaves the line open — a missing final println() leaves the output unterminated.

remember

Ask two questions about every loop: where does it start, and where can it stop early? Here the answers are 2 and “at the first divisor” — and together they are the difference between 95 tests and 8.

Then ask what the method returns. A boolean answer can drive an if anywhere; a printed line can only be read by a human.

Check your understanding

For n = 10: how many times is isPrime called, how many modulo operations happen in total, and why is isPrime(9) more expensive than isPrime(10)?

9 calls — one for each of 2 … 10. Eight modulo tests: 4, 6, 8, 10 stop at i = 2 (four tests), 5 and 7 test only 2 (two more), 9 tests 2 and then 3 (two more), and 2 and 3 run no test at all because 2 <= √2 and 2 <= √3 are both false. isPrime(10) returns at the very first test because 10 is even; 9 is odd, so it survives i = 2 and must also try i = 3. Odd composites always cost at least two tests.

One more

The last prime printed for n = 20 is 19 and the output ends … 17 19 — where does that final space come from, and what would remove it?

From System.out.print(i + " "): the space is concatenated after every printed number, including the last one, because the method cannot know that the current number is the last. pInRange never looks ahead and keeps no “first prime” flag. To remove it you would have to either build the line and strip the last character, print the separator before each prime except the first (using a boolean flag), or store the primes and use String.join(" ", …) — all three change the method's design, not just its formatting.

later

Two threads run forward from here. The algorithmic one is sieving: replacing n independent primality tests with one marking pass, which is the standard way to think about “compute for a whole range” problems. The design one is returning results instead of printing them: give pInRange an int[] or a StringBuilder return type and the caller regains control over formatting, counting and reuse — the same lesson as the previous program's return-code analysis, one level higher.

11 Your original Java source

PrimesInRange.java — verbatim

Reproduced exactly as submitted. Nothing on this page has altered it.

PrimesInRange.java 
import java.util.Scanner;

public class PrimesInRange {

    public static boolean isPrime(int num) {
        if (num < 2) {
            return false;
        }
        for (int i = 2; i <= Math.sqrt(num); i++) {
            if (num % i == 0) {
                return false;
            }
        }
        return true;
    }

    public static void pInRange(int num) {
        for (int i = 2; i <= num; i++) {
            if (isPrime(i)) {
                System.out.print(i + " ");
            }
        }
    }

    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        System.out.println();
        System.out.println("Enter max value : ");
        int n = sc.nextInt();
        System.out.println();
        if (n < 2) {
            System.out.print("Invalid Input!!");
        } else {
            pInRange(n);
        }
        System.out.println();
        sc.close();
    }
}

12 Next learning step

Where this leads

The natural candidate: a sieve

This program answers “which numbers up to n are prime?” by asking n separate questions. A sieve of Eratosthenes answers it by crossing out multiples: start with a boolean array of size n + 1, mark 0 and 1, then for each prime p you find, mark 2p, 3p, 4p … as composite.

It builds directly on what you just wrote — isPrime stays as the reference answer you can test the sieve against, the range loop becomes the outer p scan, and the boolean return becomes an array you fill once and read many times. The payoff is visible: O(n log log n) time instead of O(n√n), with O(n) space.

What carries forward

  • Decomposition — one method decides, another repeats; never mix the two jobs.
  • Early exit — the first witness ends the search, no flags required.
  • Bound reasoning — √n from the divisor-pair argument, 2 from the definition of prime.
  • Return types as design — void + printing is a dead end; a returned collection is reusable.
  • Guarding input — hasNextInt() before nextInt() is still the missing piece.
  • Cost awareness — per-call √n is cheap; n calls is not.
