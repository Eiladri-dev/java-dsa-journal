01 Program objective

What this program is actually trying to do

The program reads one integer from the keyboard and answers a single question: is this number prime, composite, equal to one, or outside the range the implementation is willing to reason about? On the way to that answer it prints every divisor it finds, and it takes the final verdict from one integer returned by a helper method.

purpose

Classify a number typed at run time. If the number is greater than one, the program reports each integer between 2 and num − 1 that divides it evenly, then prints whether the number is prime. If the number is 1, it prints the special message. If the number is 0 or negative, the method prints an invalid-input notice instead of classifying.

The problem it solves is the classic primality check, but with a twist in how the answer travels: the method does not return a boolean. It returns the number of divisors it counted, and main interprets that quantity as a verdict.

learning

Moving logic out of main into a static method that takes a parameter and returns a value — then letting that returned value drive an if / else if chain in the caller.

  • parameter passing: num receives a copy of n;
  • return values and sentinel codes (−1, −2);
  • a for loop used as trial division with a counter;
  • a do-while loop that repeats until a task is marked “complete”;
  • reading console input with Scanner.

behaviour

Printed by main: What's your number? — then it blocks on input.

Printed by isPrime: one i is a divisor line per divisor found, or the two-line invalid-input notice.

Printed by main again: exactly one classification line for a valid number.

For 0 or a negative number the loop does not stop — the prompt reappears, because no branch in main handles the value −2.

02 Problem statement

The task, stated without the code

Read one decimal integer from standard input. Determine whether it is prime. Announce the divisors you used to decide. Then stop — but only if the number landed in one of the three cases the driver loop knows how to finish.

Input, output, rules

Input. A single integer token typed at the prompt What's your number? . Each run of the loop consumes exactly one token, read with sc.nextInt(). Only a valid int is accepted: no decimals, no words, nothing outside −2,147,483,648 … 2,147,483,647.

Output. For num > 1: zero or more lines of the form i is a divisor, followed by one verdict line — either n is a Prime no. or Hence, n is NOT a Prime no.. For num == 1: the line 1 is neither prime nor composite. For num < 1: the notice invalid input !, the hint CTRL+C to Exit, a blank line, and then the prompt again.

Rules. Trial division: for every i from 2 up to num − 1, if num % i == 0 then print i and increment count. Return count. The caller decides: positive count means composite, zero means prime, −1 means the number was 1, −2 means the number was rejected.

Constraints. All arithmetic stays inside int. The divisor scan is linear in num, so a large prime makes the program sit silently for a very long time. There is no try / catch around the input read.

03 Core logic & approach

Count first, decide later

The main idea is to avoid returning a boolean and returning evidence instead. isPrime does not decide anything: it walks the candidate divisors, prints each one that divides evenly, and hands back how many it found. All interpretation happens in the caller.

1 · num == 1 ?
Yes → count = -1, no printing, method returns immediately afterwards. This case is handled first, before any arithmetic.
↓ no
2 · num < 1 ?
Yes → print the invalid notice, count = -2. One test covers both 0 and every negative number.
↓ no
3 · num > 1 ?
Yes → run the trial-division loop from i = 2 while i < num. Every num % i == 0 prints a divisor line and increments count.
↓
return count
The caller receives 0, a positive number, −1 or −2 — and that single integer carries the entire result.

Because the three tests are an if / else if / else if chain, at most one of them can run, and the method always returns exactly one integer on every path.

Why these steps work

A number greater than one is prime exactly when nothing in the range 2 … num − 1 divides it. So an empty divisor list — count == 0 — is a proof of primality, and any divisor at all is a proof of compositeness. The count itself is never needed for the verdict; only “zero or not” matters. It is used anyway, because it is already there and it makes the printed output self-explanatory.

The loop starts at i = 2 because every integer is divisible by 1, which would be a useless hit. It stops at i < num rather than i <= num because every number divides itself; counting that would label every input composite. This strict inequality is also what lets 2 and 3 work without a special case: for num = 2 the condition 2 < 2 is false before the first iteration, so the loop body never runs and the count stays 0.

The three-way split in the method exists because the loop cannot describe numbers below 2. Zero is divisible by everything, and negatives behave oddly under Java's % operator, so the implementation refuses them outright and encodes the refusal as −2 — a value the counting logic can never produce on its own, since a count is never negative.

Finally, the do-while in main runs the body before testing anything, so the prompt always appears at least once, and completion works as a one-shot latch: the first handled classification sets it to 1 and ends the loop.

Only the num > 1 path can produce a positive count, only the not-composite case can produce a zero, and the two negatives are hand-written sentinels. The caller reverses this mapping to classify the input.
04 Key Java concepts

What the code is actually demonstrating

Eight ideas are load-bearing here. Each card states what the concept does in this program, why it is used, and what to carry forward.

static method

isPrime is declared static, so main — also static — calls it by name with no object in between. The method has no fields to remember: every call starts from count = 0.

Why: the computation is a pure function of its argument, so an instance of PrimeNo would carry no information. Learn: static methods can only see static state; the whole result has to travel through parameters and the return value.

parameter

n in main is passed as an argument; num in the method receives a copy of that int. Nothing that happens to num inside could change n.

Why: the caller keeps its own value for the final message ("Hence, " + n), while the method works with an identical number under a different name. Learn: Java is pass-by-value, always — even for objects, the value that is copied is the reference.

return value

The method returns an int, not a boolean. That int is read in main as int isPrime1 = isPrime(n); and then tested three times.

Why: a single int can encode more than two outcomes — the design needs four (prime, composite, one, invalid). Learn: the return type is a contract; here it is used as a small result code, which is compact but easy to misread.

if / else if

Two chains exist: one inside the method (three tests) and one inside main (three tests on the returned value). In both, once one condition is true the rest are skipped.

Why: the cases are mutually exclusive by construction, so an exclusive chain matches the problem exactly. Learn: put the narrowest, most specific test first — here num == 1 precedes the broader num < 1 for readability, though either order gives the same result.

for loop

for (int i = 2; i < num; i++) is a bounded scan. The loop variable i exists only inside the loop; its final value after the loop ends is num.

Why: trial division needs every candidate exactly once, in order. Learn: the condition is tested before each iteration, which is why a loop over num = 2 performs zero iterations — the boundary case that a naive implementation often breaks.

do-while

do { ... } while (completion < 1); runs the prompt-and-classify body first, then checks. The body cannot be skipped.

Why: the program must ask at least once, and it may need to ask again after a rejected input. Learn: completion is the loop's exit condition, so every path that should finish must increment it — the reason the invalid path never terminates.

Scanner

new Scanner(System.in) plus sc.nextInt() reads the next integer token, skipping whitespace. It throws InputMismatchException when the token is not a valid int.

Why: the simplest way to get typed input in a console program. Learn: hasNextInt() exists precisely so you can test before you read; without it, one bad keystroke ends the program with a stack trace.

counter

int count = 0; accumulates with count++ once per divisor. It is written to twice as a sentinel (−1, −2) before the loop ever runs.

Why: one variable serves as accumulation buffer and as the method's output channel. Learn: reusing a counter for control codes works, but it removes the guarantee that the variable means one thing — a named constant or an enum would keep it honest.

08 Edge cases, correctness & limitations

What the implementation does — and what it does not

Limitations in this implementation

  • The −2 signal is never handled. main tests > 0, == 0 and == -1; the fourth possible return value matches nothing, so the invalid path cannot end the loop. The message says “CTRL+C to Exit” because that is, literally, the only exit from this state.
  • No input validation before parsing. A letter, a decimal or an out-of-range integer makes sc.nextInt() throw. There is no hasNextInt() guard and no try / catch, so the program terminates with a stack trace.
  • The loop is linear in the input value. A large prime such as 2,147,483,647 would require about 2.1 billion modulo operations — indistinguishable from a hang.
  • Names and messages disagree with behaviour. A method called isPrime returns a divisor count, not a boolean; the variable holding it is called isPrime1 but holds an int; the message “invalid input” is printed by the helper, not by the driver.
  • sc.close() is unreachable on the invalid path, and the sentinel values −1/−2 are magic numbers duplicated in two methods with nothing tying them together.
  • The num < 1 branch is load-bearing. Without it, 0 and negatives would fall into the loop path: the loop would not execute, count would stay 0, and every negative number would be announced as prime. Java's % keeps the sign of the dividend, so a negative input can never produce a zero remainder here anyway.

Correctness, stated carefully

For every num ≥ 2: correct. The scan covers all of 2 … num − 1, so count == 0 holds exactly when the number has no proper divisor, which is the definition of prime. There is no overflow in %, and the loop bound is strict, so no off-by-one exists at either end.

For num == 1: correct by special case. One is neither prime nor composite, and the program says so — but it says so with a branch that exists only to avoid a wrong answer, not because the loop could handle it.

For num < 1: not handled. The message is printed, but the program neither classifies the number nor exits. Whether this counts as a bug depends on intent: if the intent was “reject and stop”, the code is incomplete. If the intent was “reject and ask again”, the −2 should have incremented completion — and then it would stop after one rejection, which is also probably not what was wanted. The right fix is a separate decision in main that distinguishes “retry” from “exit”.

Not modified. The code shown in section 11 is exactly what was submitted. Everything above is analysis of that code, not a replacement for it.

What an ideal solution would do differently: return boolean for primality and handle “one” and “invalid” in the caller; stop the scan at i * i <= num; guard input with hasNextInt(); and make the loop's exit condition depend on an explicit finished flag that every terminating path sets.

09 Time & space complexity

Linear work, constant memory

One call to isPrime(n) with n > 1 performs exactly n − 2 loop iterations. Each iteration does one modulo and one comparison, both constant-time for int.

Time — Θ(n)

The loop bound is the input value itself: for (int i = 2; i < num; i++). Nothing shortens it — for a prime, every single candidate is tested and rejected. So the running time grows in direct proportion to the number typed, not to the number of digits in it.

That distinction matters. A 7-digit input can mean a billion iterations: doubling the value doubles the work, and adding one digit multiplies it by ten. For n ≤ 1 the cost is Θ(1) because no loop runs at all.

Space — Θ(1)

Auxiliary space does not grow with the input. The method allocates one int count and one int i; main holds completion, n and isPrime1. The Scanner wraps a buffered input stream whose buffer is a fixed size, not a function of n. Nothing is stored per divisor — each divisor is printed and forgotten, which is exactly why the count only survives as a number.

Does the analysis change anything?

Only the loop's upper bound matters. Since factors come in pairs, testing up to i * i <= num is enough: if num has a divisor greater than its square root, it must have one smaller too. That single change moves the cost from Θ(n) to Θ(√n) — for num = 10⁶, from about a million tests to a thousand.

The submitted code does not do this; it scans the full range. For small practice inputs the difference is invisible, which is why the limitation is easy to miss.

10 Takeaways & future connections

What this program teaches

lesson

A method's return value is the whole conversation between it and its caller. isPrime never prints a verdict and main never computes a divisor — yet together they classify the number. Once you see the return value as a signal, you can predict the transcript before running it: positive → composite, zero → prime, −1 → one, −2 → silence.

mistakes to avoid

  • Encoding several outcomes in magic ints with no named constants — one forgotten case and the loop never ends.
  • Forgetting that a do-while exits only when its condition changes; an unhandled branch means an unhandled loop.
  • Reading input with nextInt() without checking hasNextInt().
  • Naming a method for the answer it sometimes gives instead of what it returns.
  • Assuming “it compiled and worked for 7 and 12” means the program handles all input.

remember

Draw the contract before writing the caller: for each value the method can return, what should main do? If a value can escape without a decision, that is a hole in the design, not a detail to patch later.

And keep the boundary thinking: i < num versus i <= num is the difference between a prime checker and a program that calls everything composite.

Check your understanding

For input 9: how many divisor lines appear, what does isPrime(9) return, and which branch in main runs?

One line — 3 is a divisor — because the only integer in 2…8 that divides 9 is 3 (9 itself is excluded by i < num). count becomes 1, so isPrime returns 1, and main takes the first branch isPrime1 > 0: it prints Hence, 9 is NOT a Prime no. and sets completion = 1, ending the loop.

One more

Why does entering 0 leave the prompt on screen instead of ending the program?

Because isPrime(0) returns −2, and main only checks > 0, == 0 and == −1. No branch matches, so completion is never incremented; the condition completion < 1 stays true and the do-while starts another pass, printing the prompt again. The only escape is Ctrl+C or entering a number the program knows how to finish.

later

Primality testing is the doorway to a whole family of algorithms you will meet again: the √n optimisation is the first step towards sieve-based methods, and the same “check for a witness, stop early” pattern reappears in searching, factoring and cryptography. The return-code idea also grows into real Java types — boolean, enum, Optional, and exceptions — each of which is a more explicit way of saying what this program says with 0, −1 and −2.

11 Your original Java source

PrimeNo.java — verbatim

Reproduced exactly as submitted, including the comment and the unhandled −2 path. Nothing on this page has altered it.

PrimeNo.java 
import java.util.Scanner;

public class PrimeNo {

    public static int isPrime(int num) {
        int count = 0;

        if (num == 1) {
            count = -1;
        } else if (num < 1) {
            System.out.println("invalid input ! \nCTRL+C to Exit\n");
            count = -2;
        }

        // only for n>1
        else if (num > 1) {
            for (int i = 2; i < num; i++) {
                if (num % i == 0) {
                    System.out.print(i + " is a divisor\n");
                    count++;
                }
            }
        }
        return count;
    }

    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        int completion = 0;

        do {
            System.out.println("What's your number? ");
            int n = sc.nextInt();
            int isPrime1 = isPrime(n);
            if (isPrime1 > 0) {
                System.out.println("Hence, " + n + " is NOT a Prime no.");
                completion++;
            } else if (isPrime1 == 0) {
                System.out.println(n + " is a Prime no.");
                completion++;
            } else if (isPrime1 == -1) {
                System.out.println("1 is neither prime nor composite");
                completion++;
            }

        } while (completion < 1);
        sc.close();
    }
}

12 Next learning step

Where this leads

Direction, not yet a destination

The obvious continuation is to keep everything this program already does and change only how the answer travels: return a boolean from the checker, keep 1 and the invalid case in the caller, and give the driver loop an explicit finished flag so every path can end it. Same behaviour, cleaner contract — a natural way to practise method design without learning a new topic.

The other direction is the loop bound: stopping at i * i <= num and comparing the iteration counts against this version.

Not confirmed. No specific next program has been chosen for your sequence yet — both options build directly on static methods, parameters, return values and conditional logic, and either can be picked once your course order is settled.

What carries forward

  • Method contracts — every value a method can return needs a decision at the call site.
  • Loop exit conditions — a do-while is only as safe as the set of paths that mutate its condition.
  • Input robustness — hasNextInt() before nextInt() is a habit worth forming now.
  • Boundary arithmetic — strict versus inclusive comparisons decide whether 2 is prime.
  • Cost awareness — trial division is Θ(n); every later prime algorithm is measured against it.
