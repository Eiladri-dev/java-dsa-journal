01 Program objective

What this program is actually trying to do

Read a number that is supposed to be written in binary, evaluate its positional value in base 10, and print Decimal : …. If the number is negative, print Invalid Input. and start the whole program again by calling main from inside itself.

purpose

Convert a binary numeral to decimal. The digits are pulled off the number one at a time, right to left, with % 10. Each digit is multiplied by a weight — 1, 2, 4, 8, 16 … — supplied by powerOfTwo, and the products are summed into dec.

The program demonstrates positional notation: in base 2 a digit's contribution depends on how far it sits from the right, and that distance is the exponent.

learning

A second look at digit extraction, this time with a per-position weight instead of a per-position count.

  • a helper method that computes a power, called once per digit;
  • while + % 10 + /= 10 as a “peel the last digit” idiom;
  • an accumulator (dec += a) and a position counter (pow++) advanced together;
  • long instead of int for the input and the powers;
  • an if / else if chain with a fall-through return -1;
  • a method calling main — recursion used as a restart mechanism.

behaviour

Printed first: Enter no in binary : with print, so your digits appear on the same line, right after the colon.

After a non-negative input: one line, Decimal : X, then the program ends.

After a negative input: Invalid Input., then the prompt again — because main was called recursively, not re-entered by a loop.

After a non-numeric token: an InputMismatchException at line 23, with no message printed by the program.

02 Problem statement

The task, stated without the code

Given a numeral whose digits are meant to be binary, compute the integer it denotes and print it. Given a negative number, refuse and ask again. Given anything that is not a whole number, the program has no plan at all.

Input, output, rules

Input. One integer token read with sc.nextLong(), typed immediately after the prompt on the same line. The digits are supposed to be 0s and 1s, but nothing enforces that: 12, 102 and 9999 are all accepted and silently evaluated.

Output. For num ≥ 0: exactly one line, Decimal : dec. For num < 0: Invalid Input., then a fresh run of the program (a new prompt, and whatever the next input produces).

Rules. Write the number's decimal digits as d0, d1, … from the right. Its value is Σ dk · 2k. The loop implements exactly that: extract num1 % 10, multiply by powerOfTwo(pow), add, then num1 /= 10 and pow++.

Constraints. Digits are read in base 10 (% 10), so a “digit” can be 0…9. No validation of the binary alphabet. The powers are recomputed per digit, so the work grows quadratically with the digit count. Each negative input costs one extra stack frame permanently.

The power == 1 branch is also redundant. Deleting it changes nothing, because the loop with power = 1 multiplies once and also returns 2. It is harmless — just an unnecessary special case.

03 Core logic & approach

Weights, not counters

The whole conversion is four statements inside one loop. Each pass takes the rightmost digit, prices it by its position, adds the price, and removes the digit. The helper exists only to answer “what is 2 to the power of this position?”.

One pass of the loop, dissected

lines 29–34repeated while num1 > 0
while (num1 > 0) {
    long a = (num1 % 10) * powerOfTwo(pow);   // ① take the digit, price it
    pow++;                                    // ② the next digit is worth twice as much
    num1 /= 10;                               // ③ throw the digit away
    dec += a;                                 // ④ add the price to the total
}

① num1 % 10 isolates the last decimal digit — and powerOfTwo(pow) supplies its weight. For 1011 the first product is 1 × powerOfTwo(0) = 1 × 1.

② pow is the position of the next digit. Because we always read right to left, it just increments: 0, 1, 2, 3.

③ Integer division by 10 deletes the digit we just used: 1011 → 101 → 10 → 1 → 0. The loop ends when nothing is left, so its length is exactly the digit count.

④ dec is a plain accumulator. Order does not matter for addition, so the fact that we visit the digits in reverse is invisible in the result.

Because the digits are extracted in base 10, the value of a digit can be 0 … 9 — the program never checks that it is 0 or 1. That single omission is the biggest difference between what the program says and what it does.

Why the maths is right

Positional notation says a numeral's value is the sum of each digit times the base raised to the digit's distance from the right. In base 2 the weights are 1, 2, 4, 8, 16 … — exactly what powerOfTwo(0..d−1) produces.

The loop visits the digits in the order 1s, 2s, 4s, 8s … and adds the contributions, so the total is the same as reading left to right. For 1011:

passdigitpowweightproductdec
11011 % 10 = 10111
2101 % 10 = 11223
310 % 10 = 02403
41 % 10 = 138811

A zero digit contributes nothing but still consumes a position — that is why pow is incremented before num1 is divided: if it were not, 1011 and 111 would both total 11.

Why the helper is called so often

powerOfTwo has no memory. Asking for 23 means multiplying 1 by 2 three times, from scratch, even though the previous call already computed 22. For 4 digits that is 5 multiplications; for 19 digits it is 170. A single variable — “the weight of the current position” — doubled after each pass would do the same job with one multiplication per digit.

What is genuinely good here. The digit loop is textbook: % 10 to read, / 10 to advance, and a condition that terminates naturally. That idiom will come back in palindrome checks, digit sums, and base conversions in the other direction.
04 Key Java concepts

What the code is actually demonstrating

Nine ideas are load-bearing here. Each card says what the concept does in this program, why it is used, and what to carry forward.

long data type

Both the input and powerOfTwo's return type are long. That allows a 19-digit number to be typed instead of 10, but the values produced here never come close to needing it.

Why: defensive choice — 2p doubles fast. Learn: long does not protect you from overflow forever; 263 is the wall, and repeated doubling reaches it quickly.

value-returning method

powerOfTwo(int power) takes a position and returns the weight for it. The caller multiplies the two numbers together: (num1 % 10) * powerOfTwo(pow).

Why: the exponent logic is separate from the digit logic, so each can be read alone. Learn: a method call can appear anywhere a value of its type could — including inside an arithmetic expression.

if / else if + fallback

Three tests — == 0, == 1, > 1 — followed by a bare return -1; that catches everything else.

Why: the compiler requires a return on every path, and the chain as written does not cover negatives. Learn: a final unconditional return is how you satisfy that rule — but here it also silently encodes “negative power” as −1, which the caller would happily multiply by.

for loop as exponentiation

for (int i = 0; i < power; i++) a = a * 2; — repeated doubling instead of a library call. It runs exactly power times, so powerOfTwo(3) ends with 8.

Why: it shows what an exponent really is — repeated multiplication. Learn: a count-controlled loop is ideal when the number of repetitions is the input, as it is here.

while + % + /=

The digit loop cannot use a for, because the number of digits is not known until the number is read. num1 % 10 reads a digit, num1 /= 10 deletes it, and the loop ends when the value reaches 0.

Why: it terminates by itself for every non-negative input. Learn: “peel and shift” is the standard decimal-digit idiom — % 10 then / 10, always together, always in that order.

accumulator + position

dec += a accumulates the value; pow++ tracks the position. They are separate variables because they mean different things — one is a sum, the other an index.

Why: mixing them would break the weight progression. Learn: a loop often needs two independent “suitcase” variables, one for the answer and one for where you are.

recursion as retry

main(args); inside the invalid branch starts a brand-new run: new Scanner, new num, new prompt. The old frame stays alive, waiting for the inner one to return.

Why: it reuses the whole program as its own retry mechanism. Learn: recursion is a stack of unfinished work — each retry costs a frame and a Scanner that is only closed when the stack unwinds.

Scanner · nextLong

sc.nextLong() parses one token as a long. Letters, decimals, or a number beyond long's range throw InputMismatchException, which nothing catches.

Why: it accepts bigger inputs than nextInt(). Learn: hasNextLong() exists so you can test before you read — and every recursion level opens its own Scanner, which is a resource leak you would not get from a loop.

print vs println

The prompt uses print so the typed digits sit on the same line; the results use println so each ends cleanly. In the invalid branch the println also supplies the line break that puts the next prompt on a fresh line.

Why: prompts and results have different layout needs. Learn: print leaves the cursor where it is — which is exactly what you want when you are about to ask for input.

Normal input — 1011

Four passes, weights 1, 2, 4, 8, and the three non-zero digits contribute 1 + 2 + 8 = 11. The zero digit still consumed the weight 4 — it just multiplied it to nothing. Five multiplications happen inside the helper, none of them visible.

Edge — 0

num1 = 0 makes the loop condition false immediately: zero passes, zero helper calls, dec stays at its initial 0, and the program prints Decimal : 0. It is the only input that reaches the output without ever entering the loop — and it happens to be correct, because 0 in binary is 0.

The limitation — 102, 9999

These are not binary numbers, yet the program evaluates them without complaint: 102 becomes 6 and 9999 becomes 135. Nothing checks that a digit is 0 or 1, so any decimal digit is treated as a legitimate coefficient of a power of two. A real converter must reject these.

Invalid — −101 then abc

A negative number skips the loop, prints Invalid Input., and calls main again — watch the depth counter climb with every rejection. abc is not a rejection: nextLong() throws at line 23 and the program dies on whichever frame is currently on top, leaving every outer frame (and its Scanner) still open.

08 Edge cases, correctness & limitations

What the implementation does — and what it does not

Limitations in this implementation

  • No binary validation. The loop reads base-10 digits, so 2 … 9 are accepted as coefficients. Any number can be typed and every number gets an answer — most of them meaningless. This is the bug that matters most: the program is named Bin2dec but converts any decimal-digit numeral as if it were binary.
  • main calls itself instead of looping. Each invalid input adds a stack frame that stays alive until the innermost run finishes; a few thousand rejections end in StackOverflowError. A while around the input would cost nothing.
  • A new Scanner per frame. Every recursive call constructs another Scanner(System.in). Only the innermost is closed while the stack is deep; the outer close() calls run later, as the frames unwind.
  • Validation happens after the work. The negative test sits below the loop, and it only works because a negative input makes the loop condition false. Put the same test above the loop and the behaviour would be identical but the intent obvious.
  • The helper recomputes every power. powerOfTwo(3) re-multiplies from 1, even though the caller already had 4. Cost is d(d−1)/2 multiplications instead of d.
  • Dead and redundant branches. return -1; is unreachable (pow is never negative, and 0 and 1 are handled above), and the power == 1 case could be left to the loop.
  • Input is unguarded. No hasNextLong(), no try / catch: a typo produces a stack trace instead of a message, and it happens on whatever frame is innermost at the time.
  • The class name is lower-case in the middle (Bin2dec). Legal Java, but the convention is BinToDec or BinaryToDecimal.

Correctness, stated carefully

For inputs made only of 0s and 1s: correct. Each pass contributes d·2k for the digit at position k, and every position from 0 to the digit count minus one is visited exactly once — so the sum equals the numeral's base-10 value. 0, 1 and 100000 are all handled by the same loop with no special cases.

For inputs containing 2 … 9: wrong, but confidently so. No branch rejects them, so the program returns a plausible number computed from invalid digits. Nothing in the transcript signals the mistake — the same class of silent wrongness as Integer.parseInt never having been attempted. A real converter needs a digit test inside the loop, for example if (num1 % 10 > 1) → invalid.

For negative numbers: rejected, by recursion. The output is correct as a message, but the mechanism is fragile: the retry is unbounded, the resource cost grows with each rejection, and the eventual failure mode is a StackOverflowError rather than a graceful exit.

For non-numeric input: not handled. nextLong() throws before any of the program's own logic runs.

09 Time & space complexity

Quadratic in the digit count, but tiny in practice

The loop runs once per digit. The helper, however, rebuilds its power from scratch every time, so the total work is triangular: 0 + 0 + 2 + 3 + … + (d−1) multiplications for a d-digit number.

Time — Θ(d²) inside the helper

The while loop performs d passes, each calling powerOfTwo once. That helper does p multiplications for a power p ≥ 2 (and none for 0 or 1), so the run totals Σ p = (d−1)d/2 − 1 multiplications, plus d divisions and d remainders. Asymptotically that is Θ(d²).

Space — Θ(1) per frame, Θ(k) for k retries

One run of main needs a handful of scalars — num, num1, pow, dec, a — and one Scanner with a fixed buffer. Nothing grows with the number of digits.

The recursion is what changes that: k rejected inputs leave k suspended main frames and k open Scanners alive simultaneously. Memory is therefore Θ(k) in the number of retries, and the JVM's default stack depth (thousands of frames) is the hard ceiling.

What would make it linear

Keep the weight in a variable and double it each pass: weight = 1; … weight *= 2; — one multiplication per digit, Θ(d) total, and the helper disappears. The bitwise form 1L << pow is O(1) per digit and exact for pow < 63. Neither changes the output for a single digit; both change how the code reads — one clear shift instead of a loop that re-earns its answer.

10 Takeaways & future connections

What this program teaches

lesson

Digit extraction is universal; the weight is what changes between bases. % 10 and / 10 peel decimal digits no matter what those digits are supposed to mean. The program is a correct base-2 evaluator and an unvalidated base-10 reader at the same time — and that gap is the whole story of this file.

mistakes to avoid

  • Accepting digits 2 … 9 in a program whose name promises binary input.
  • Validating after the computation instead of before it.
  • Using recursion to re-run a program when a while loop would do — every retry leaks a frame and a Scanner.
  • Recomputing a power from scratch on each call instead of carrying it forward.
  • Leaving a return -1; fallback that the caller never checks for.
  • Trusting nextLong() on unvalidated input.

remember

A number's type and its meaning are separate. 1011 is a perfectly ordinary long; calling it “binary” is a promise the code has to keep by checking each digit.

The other lesson is quieter: the loop that already knows how to move a value forward is almost always cheaper than a method that rebuilds it.

Check your understanding

For the input 1011: how many times is powerOfTwo called, what does the third call return, and how many multiplications happen inside the helper in total?

Four calls, for powers 0, 1, 2 and 3. The third call is powerOfTwo(2) and returns 4: a starts at 1, the loop multiplies it twice, giving 2 then 4. Total multiplications inside the helper: 0 (power 0) + 0 (power 1) + 2 (power 2) + 3 (power 3) = 5. The four passes of the outer loop contribute dec = 1 + 2 + 0 + 8 = 11.

One more

Entering -101 prints Invalid Input. and asks again. Why does entering -101 twenty thousand times eventually crash instead of just asking twenty thousand times?

Because the retry is a recursive call, not a loop. Each −101 leaves its main frame suspended at line 38 — with its own Scanner still open — and starts a new frame on top. Twenty thousand rejections means twenty thousand live frames, and the JVM's thread stack cannot hold that many: it throws StackOverflowError. A while loop would reuse one frame and one Scanner forever, printing the message as many times as you like. The stack also explains the ordering: nothing from the outer frames (including their sc.close() calls) runs until the innermost main finally returns.

later

The reverse direction — decimal to binary — is the natural complement, and it makes the weight idea concrete: repeatedly divide by 2, collect the remainders, and read them back to front. From there the same machinery becomes bit operations: 1L << k for the weight, & to test a bit, | to set one, and >>> to shift a number down a place — operations that do exactly what this loop does by hand, in constant time. The recursion-as-retry pattern, meanwhile, is the anti-pattern that later makes the case for the loop-based menus you will write in bigger programs.

11 Your original Java source

Bin2dec.java — verbatim

Reproduced exactly as submitted. Nothing on this page has altered it.

Bin2dec.java 
import java.util.Scanner;

public class Bin2dec {
    public static long powerOfTwo(int power) {
        if (power == 0)
            return 1;
        else if (power == 1)
            return 2;
        else if (power > 1) {
            long a = 1;
            for (int i = 0; i < power; i++) {
                a = a * 2;
            }
            return a;
        }
        return -1;
    }

    public static void main(String[] args) {

        Scanner sc = new Scanner(System.in);
        System.out.print("Enter no in binary : ");
        long num = sc.nextLong();

        long num1 = num;
        int pow = 0;
        long dec = 0;

        while (num1 > 0) {
            long a = (num1 % 10) * powerOfTwo(pow);
            pow++;
            num1 /= 10;
            dec += a;
        }

        if (num < 0) {
            System.out.println(("Invalid Input."));
            main(args);
        } else {
            System.out.println("Decimal : " + dec);
        }
        sc.close();
    }
}

12 Next learning step

Where this leads

The natural candidate: decimal → binary

Your sequence has now converted from a base; the mirror program converts to one. Divide repeatedly by 2, keep the remainders, and read them back in reverse — the same “peel the last digit” reflex, with the weights replaced by a division that decides each digit.

The interesting part is what it teaches about this program: once you have written both directions, the weight table (1, 2, 4, 8 …) stops being something to recompute and becomes something you carry — a single variable that doubles. That is the exact change suggested in section 9, and it makes the quadratic cost disappear.

What carries forward

  • Peel and shift — % 10 to read, / 10 to advance, in that order, always.
  • Positional meaning — the same digit is worth ten times more one place to the left; in base 2, twice as much.
  • Validate before compute — a digit test inside the loop would have caught 102.
  • Loops over recursion for retries — one frame, one Scanner, unbounded attempts.
  • Carry, don't recompute — a running weight beats a helper that rebuilds the same power.
  • Guard the read — hasNextLong() before nextLong().
