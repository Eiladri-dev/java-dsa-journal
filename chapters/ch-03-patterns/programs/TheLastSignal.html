01 Program objective

What this console is actually doing

A station has lost contact with Earth. The program is the only interface left: it takes a call sign, a radius and a three-digit code, derives a checksum from the code's digits, turns that number into a telemetry status and an authorisation decision, and draws the containment sigil only if the operator passes.

purpose

Authenticate an operator, then act on the result. The console reads three values, computes one derived number (checkSum), and uses it twice: once for telemetry (% 2) and once for authorisation (% 3).

Everything after that is conditional. Granted, the sigil is rendered and the report claims containment. Denied, no sigil exists and the report must admit lockdown.

learning

  • while validation that re-prompts instead of continuing;
  • digit extraction with % 10 and / 10;
  • two static helpers — a computation and a renderer;
  • a shape described by four coordinate equations, not by rows;
  • one grid, one row loop, one column loop, no half-printing;
  • reporting that must match the branch that actually ran.

behaviour

Three prompts, each with validation. Invalid radius (outside 1–4) or invalid code (outside 100–999) prints a rejection and asks again — forever, until a legal value arrives.

Then a single decision point: checkSum % 3. One branch prints the diamond and the restored message; the other prints a denial and the lockdown message.

Output is deterministic for a given set of inputs, because nothing else is read.

02 Problem statement

The task, stated without the code

Read three validated values. Sum the digits of the access code. Report telemetry from the parity of that sum, authorise on divisibility by three, draw a hollow diamond of radius R if and only if authorisation succeeds, then print a report that tells the truth about what happened.

Constraints that shape the code. One row loop and one column loop for the sigil. Star positions derived mathematically, with no per-row lists and no separate upper/lower halves. The diamond stays hollow for R = 1, 2, 3 and 4. A denied run must not print a sigil and must not claim restoration.

Two independent tests on one number. Parity decides telemetry, divisibility by three decides access. A code can therefore be STABLE and still be denied — 583 sums to 16, which is even but not a multiple of 3. The two outputs are not linked.

03 Core logic & approach

Three decisions, one number, four equations

The console has a linear spine — read, validate, compute, decide, render, report — and one place where the work becomes geometry: four arithmetic conditions standing in for the four edges of a diamond.

The sigil as four equations

DiamondRender(int radius)one grid, four edges
for (int outerRow = 1; outerRow <= (2 * radius + 1); outerRow++) {

    }
    System.out.println();
}

why sums are diagonals

Step one cell right and one cell down: r + c grows by 2, r − c stays the same. A constant difference is therefore a line running down-right; a constant sum is a line running down-left. Two of each make the four edges.

why the constants

The grid is 2R+1 wide, so the vertices are at c = R+1 (top and bottom) and r = R+1 (left and right). Substituting the top vertex into r + c gives 1 + R + 1 = R + 2; the bottom vertex gives 2R+1 + R+1 = 3R + 2. The two difference edges need the constant R to pass through those same corners.

why 4R stars

Each of the four edges holds R + 1 cells, and the four vertices are each shared by two edges. So the total is 4(R + 1) − 4 = 4R: 4, 8, 12, 16 for R = 1…4. Everything else — (2R+1)² − 4R cells — prints two spaces, which keeps the interior hollow.

04 Key Java concepts

What the code is actually demonstrating

Nine ideas carry this console. Each card says what the concept does here, why it is used, and what to carry forward.

validation loops

while (R < 1 || R > 4) { … R = scanner.nextInt(); } — the read happens inside the loop, so an illegal value cannot escape.

Why: the prompt is a promise that the next value is usable. Learn: validate with a loop that re-reads, never with a single if that continues anyway.

digit extraction

% 10 gives the last digit, / 10 removes it. Repeating until the number is zero visits every digit exactly once.

Why: the checksum must be computed, not stored. Learn: this pair is the standard way to read a number's digits without converting it to a String.

integer division

5 / 10 is 0 in Java, not 0.5. That truncation is what ends the loop: the last digit leaves a zero behind.

Why: the loop condition is > 0, so it relies on truncation. Learn: with int maths, division is a floor towards zero — the same rule that makes 5 / 2 + 1 = 3.

static helpers

Two public static methods split the program: checkSum computes, DiamondRender prints. main only reads, decides and calls.

Why: a calculation and a rendering have nothing to do with each other. Learn: the split is what makes each half testable — checkSum(583) can be checked without any console output.

coordinate predicates

Every cell is decided by (outerRow, outerCol). Nothing is printed from the loop counters directly; the star question is asked as an arithmetic test.

Why: one rule must hold for every radius. Learn: describe a shape as a property of the cell, not as a list of rows.

union of edges

A hollow diamond is the boundary of four line segments. Four || conditions draw exactly the boundary — the interior never matches, so it stays blank without any special case.

Why: one grid, one pass, no upper/lower halves stitched together. Learn: hollow shapes come free when you describe the outline rather than the fill.

short-circuit ||

At the four vertices two conditions are true at once — the top cell satisfies both r + c == R+2 and c − r == R. Because the test is a boolean OR, it still prints a single star.

Why: overlapping equations must not double-print. Learn: overlapping conditions are safe only when the action is idempotent, as printing once is.

Scanner ordering

nextLine() is used for the call sign before any nextInt(). That ordering avoids the classic leftover-newline bug, where a later nextLine() would read an empty string.

Why: it happens to be safe here. Learn: nextInt() leaves the line ending in the buffer; mixing the two in the other order breaks.

conditional phases

The sigil exists only inside the if (checkSum % 3 == 0) branch. A denied run prints no diamond, and the report's last line is chosen by the same test — so the text cannot contradict the drawing.

Why: a lockdown message next to a rendered sigil would be a lie. Learn: derive every claim in a report from the same condition that produced the action.

naming & shadowing two small frictions

int checkSum = checkSum(code); is legal: the local variable is declared after the method call is resolved, and Java allows a variable to share a method's name. It compiles — but a reader has to work out which checkSum is meant on each line.

DiamondRender starts with a capital letter, which by Java convention marks a class, not a method. The code runs either way; the convention exists so other people can read it at a glance.

Also visible: the method parameter is named accessCode and is reassigned inside the loop. That is fine because it is a copy, but a parameter that changes meaning halfway is harder to follow than a separate local.

redundancy the repeated test

while (R < 1 || R > 4) { if (R < 1 || R > 4) // already known print(...); print(prompt); R = scanner.nextInt(); }

Inside a loop whose condition is exactly that test, the inner if is always true. It changes nothing about the output — it is a reading cost, not a bug. The same pattern appears in the code-validation loop.

Limitations in this implementation

          
    
            
  • A checksum is not a password. Any code whose digits sum to a multiple of 3 is admitted — exactly 300 of the 900 legal codes, one third. Worse, the sum ignores order: 583, 853 and 385 all authorise or all fail together.
    • 
            
  • Divisibility by 3 has a shortcut. Since 10 ≡ 1 (mod 3), a number and its digit sum always share the same remainder mod 3. So checkSum % 3 == 0 is mathematically identical to code % 3 == 0 — verified across all 900 codes. The checksum is still needed for the report and for telemetry, but the access decision does not actually depend on it.
    • 
            
  • Telemetry does depend on the sum. Parity is not preserved by digit sums: 100 is even while its digits sum to 1. Half of all legal codes get a different telemetry status under the two rules, which is why this one must be computed from the digits.
    • 
            
  • No type validation. A letter at a numeric prompt throws InputMismatchException. The loops guard the value but not the kind of input, so the console crashes instead of rejecting.
    • 
            
  • No attempt limit and no lockout. An operator can retry the code forever; nothing counts attempts, so a script could brute-force all 900 codes in seconds.
    • 
            
  • The call sign is never checked. Any string — including an empty one — is accepted as an operator identity, and it is echoed into the report as-is.
    • 
            
  • Formatting leaks the branch. The denied path leaves a line containing a single space and omits the blank line before the header; the two outcomes do not share a layout.
    • 
            
  • main is the only test surface. The logic is reachable only through the console, so checked correctness here came from re-implementing the methods, not from running them in isolation.
    • 
          

        


        

          
Correctness, stated carefully

          
As a specification: met. Both ranges are enforced with re-reading loops. The checksum is computed from the digits with % 10 and / 10, never stored. The diamond is one grid, one pass, four derived conditions, hollow at every radius from 1 to 4. A denied run prints no sigil, and its final line says lockdown — the report cannot claim a restoration that did not happen.

          
As a security design: theatrical. That is consistent with the fiction, and the code is honest about what it computes. But the authorisation rule admits a third of all codes and completely ignores digit order, so it is a puzzle, not a credential check.

          
As an input handler: partial. Values are validated; types are not. Everything else in the console is well behaved.

09 Time & space complexity

        
Three digits, then a square

        
The checksum costs one loop over the digits — three iterations at most. The sigil costs one pass over a square grid. With R capped at 4, the whole program is bounded at 81 cell decisions, so the analysis is interesting for what it says about scaling, not about speed.

The inner cell test is a constant amount of work: at most four comparisons plus a print. So the sigil is exactly 4R² + 4R + 1 cell visits, and the whole console is Θ(R²) in time for a granted run and Θ(1) for a denied one — the expensive part is skipped entirely.

Space — Θ(1)

          
Two loop counters, one int accumulator, three input variables and one Scanner. No array holds the grid: each cell is decided, printed and forgotten, so memory does not grow with the radius at all.

          
That is a real design choice, not an accident — the same shape could have been built in a char[][] and printed afterwards, which would cost O(R²) space for no benefit here.


          
If the radius were unbounded

          
Remove the 1–4 guard and the cost becomes O(R²) in time and output characters: each row is 2(2R+1) = 4R + 2 characters, so a full sigil is roughly 8R² characters written to the console. At R = 500 that is two million characters — still instant, but no longer something a terminal window can show.

10 Takeaways & future connections

        
What this console teaches

      


      

        

          
lesson validate by re-reading

          
A validation loop has three parts: test the value, tell the operator, read again. All three must live in the loop body — if the read is outside, the loop spins forever, and if the test is only an if, the bad value is used anyway.

          
The pattern here repeats twice with different bounds, which is exactly the point: one shape, two ranges.

        


        

          
habit derive, do not list

          
The diamond is four equations, not four row lists. That single decision is what lets DiamondRender(1) and a hypothetical DiamondRender(5) work with no edits — the shape is a property of the grid, not of a table of coordinates.

          
Which equations? Two constant sums for the down-left edges, two constant differences for the down-right ones.

        


        

          
insight one number, two meanings

          
checkSum answers two different questions: is the telemetry steady (% 2) and may this operator proceed (% 3). They are independent, and the console can be stable yet refuse access — the 2 × 2 table from section 03 is the whole design in one grid.

        

      


      

        

          
Check your understanding

          
A code can print STABLE and still be denied. Explain how, then give one code that prints DRIFT DETECTED and is granted.

          
          
The two tests look at different remainders of the same sum. 583 sums to 16: 16 is even, so telemetry is STABLE, but 16 ÷ 3 leaves 1, so authorisation fails. For the reverse, any odd multiple of 3 works — 555 sums to 15, which is odd (DRIFT DETECTED) and divisible by 3 (GRANTED). 915, 177 and 393 all behave the same way. Telemetry describes the station; authorisation describes the operator. They share an input, not a conclusion.

        


        

          
One more

          
The conditions include both r − c == R and c − r == R. Why is only one of them ever true at a given cell, and why are both needed anyway?

          
          
They describe opposite diagonals. A constant difference r − c draws a line running down-right, which gives the lower-left edge; a constant c − r draws down-left, giving the upper-right edge. For a single cell both cannot hold unless R = 0, so they never conflict — but each is needed to close one half of the outline. The two r + c conditions work the same way with the constants R + 2 and 3R + 2, one for the upper-left edge and one for the lower-right. Four edges, four equations, one boolean test.

        

      


      

        
later

        
The habit worth keeping is the one this file already shows: separate the decision from the drawing. checkSum returns a number and prints nothing; DiamondRender draws and decides nothing. Each can be reasoned about — and, in a version with a test harness, checked — on its own.

        
The next step is not about diamonds at all. It is about what happens when a program must survive input it did not expect: a letter where a number belongs, an empty call sign, an operator who keeps guessing. Handling that means reading whole lines and parsing them deliberately, which is the bridge from these console programs to any program that talks to a person.

            chkSum += (accessCode % 10);
            accessCode /= 10;
        }
        return chkSum;
    }

            for (int outerCol = 1; outerCol <= (2 * radius + 1); outerCol++) {
                if ((outerRow + outerCol) == (radius + 2) || (outerRow - outerCol) == radius
                        || (outerCol - outerRow) == radius || (outerCol + outerRow) == (3 * radius) + 2)
                    System.out.print("* ");
                else {
                    System.out.print("  ");
                }
            }
            System.out.println();
        }
    }

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        // accepting call sign (a String)
        System.out.print("Please enter your call-sign (string only) : ");
        String callSign = scanner.nextLine();

        // accepting A diamond radius R, an integer between 1 and 4
        System.out.print("Please enter diamond radius (1 - 4) : ");
        int R = scanner.nextInt();
        while (R < 1 || R > 4) {
            if (R < 1 || R > 4)
                System.out.print("Invalid Input entered... \nplease retry!\nCTRL+C to exit\n");
            System.out.print("Please enter diamond radius (1 - 4) : ");
            R = scanner.nextInt();
        }

        // accepting A three-digit access code, an integer between 100 and 999
        System.out.print("Please enter a three-digit access code (100 and 999) : ");
        int code = scanner.nextInt();
        while (code < 100 || code > 999) {
            if (code < 100 || code > 999) {
                System.out.print("Invalid Input entered... \nplease retry!\nCTRL+C to exit\n");
            }
            System.out.print("Please enter a three-digit access code (100 and 999) : ");
            code = scanner.nextInt();
        }

        int checkSum = checkSum(code);
        String telmetryStatus;
        if (checkSum % 2 == 0)
            telmetryStatus = "STABLE";
        else
            telmetryStatus = "DRIFT DETECTED";

        // auth via checksum
        if (checkSum % 3 == 0) {
            System.out.print("\nACCESS GRANTED\n");
            DiamondRender(R);
            System.out.println();

        } else {
            System.out.print("\nACCESS DENIED\n ");
        }

        System.out.println("\n===Shutdown Report====");
        System.out.println("Operator Call-sign : " + callSign);
        System.out.println("CheckSum : " + checkSum);
        System.out.println("Telemetry Status : " + telmetryStatus);
        if (checkSum % 3 == 0)
            System.out.println("CONTAINMENT RESTORED. SIGNAL ONLINE");
        else
            System.out.println("\nLOCKDOWN MAINTAINED. SIGNAL OFFLINE\n");

        scanner.close();
    }
}

Where this could go next

        
The console is complete against its own specification. The open question is what it should do with input it cannot read — and that is a different skill from the one this program practises.

      


      

        

          
Make the console survive its operator

          
Right now a letter at a numeric prompt ends the program. The fix is not a bigger while condition; it is to read a whole line, try to parse it, and treat failure as just another invalid value — the same loop, a wider notion of "invalid".

          
static int readInt(Scanner sc, int lo, int hi, String prompt) {
    while (true) {
        System.out.print(prompt);
        String line = sc.nextLine().trim();
        try {
            int v = Integer.parseInt(line);
            if (v >= lo && v <= hi) return v;
        } catch (NumberFormatException e) { }
        System.out.print("Invalid Input entered... \nplease retry!\n");
    }
}

          
One helper replaces both validation loops, and the two ranges become arguments. It also removes the nextInt() / nextLine() hazard entirely, because every read consumes a full line.
